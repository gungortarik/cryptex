# Can stock Obsidian keep managed edits inside the selected projection?

On November 25 the owner authorized a design review for Windows and macOS. I found no documented combination that meets M7 with stock Obsidian, the user's existing vault and the current M6 publisher. The best fit for that workflow is a supported Obsidian operation bound to a specific managed directory for the duration of the read or write. The public request for that guarantee still contains only the original post. This review used source and documentation only. [M7 contract](../../docs/milestones/M7_OBSIDIAN_CONTROLLED_WRITEBACK.md) · [Obsidian API request](https://forum.obsidian.md/t/api-request-physically-contained-vault-operations-for-managed-paths/119512)

## The directory can change during an ordinary refresh

The protected directory is the generated `Cryptex/` subtree. The user may have other notes alongside it in the same vault. M6 renders a replacement tree in a sibling staging directory, renames the published tree to a backup, then renames the staged tree into place. An editor can therefore retain an old note across a legitimate change of directory identity. A design must identify which projection the edit belongs to and preserve a pending manual edit for review if its base changed. An identical relative filename in the new tree is insufficient evidence to apply the edit. [M6 publisher](../../crates/projection/src/vault.rs) · [Managed edits and user-owned content](../../docs/13_OBSIDIAN_INTEGRATION.md#6-managed-note-editing)

## Alternatives assessed

| Approach | What it provides | What prevents acceptance |
| --- | --- | --- |
| Capture the open editor's text and submit a proposal to the daemon | The plugin can obtain a draft without issuing a second file read. | The editor buffer supplies no physical directory identity for the original open or subsequent save. It also misses edits made with that editor closed. It could support the review UI once the underlying boundary exists. [Obsidian API declarations](https://github.com/obsidianmd/obsidian-api/blob/737629a51f6b4d30f8336fa3d38f3df006e322d4/obsidian.d.ts) |
| Restrict the Obsidian process | Windows AppContainer can restrict a process's access. Apple App Sandbox is an entitlement on the signed application. | A process-wide grant to the vault still includes sibling notes. A Cryptex plugin cannot add an entitlement to the stock signed Mac application. The reviewed mechanisms establish no per-operation grant to the current managed subtree on both systems. [Microsoft AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation) · [Apple entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.app-sandbox) · [Earlier sandbox review](m7-p1-platform-sandbox-feasibility-20261022.md) |
| Keep the projection on a private volume without filesystem links | Windows exFAT omits hard links, soft links and mount points within the volume. macOS supports exFAT. | Mounting just `Cryptex/` makes the mount location the directory M6 needs to replace. Mounting the whole vault changes the user's storage choice and still requires binding every Obsidian operation to the intended volume and current subtree across removal, remount and refresh. Windows exFAT also lacks filesystem ACLs. Private access while mounted would need independent proof on both systems. [Microsoft filesystem comparison](https://learn.microsoft.com/en-us/windows/win32/fileio/filesystem-functionality-comparison/) · [Apple disk formats](https://support.apple.com/guide/disk-utility/file-system-formats-dsku19ed921c/mac) |

Windows documents a volume GUID path for identifying a volume. Apple's Disk Arbitration framework provides mount and unmount notifications. Neither document establishes that stock Obsidian binds a pending Vault operation to an authenticated subtree when it opens the file. An OS disk identity or notification alone cannot supply this missing contract. [Microsoft volume naming](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-volume) · [Apple Disk Arbitration](https://developer.apple.com/library/archive/documentation/DriversKernelHardware/Conceptual/DiskArbitrationProgGuide/ManipulatingDisks/ManipulatingDisks.html)

## Decision and verification threshold

Retain stock Obsidian and the existing M6 publisher. A supported directory-bound operation must cover create, read and conditional update on both OSes. It must reject stale directory identity and preserve content-conflict handling. Only the daemon may accept a reviewed proposal into canonical history. A private volume would merit separate investigation only if a dedicated vault and a change to the M6 publication lifecycle become acceptable.

Before enabling managed I/O, apply the [existing synthetic acceptance matrix](m7-p1-obsidian-api-containment-request-20261016.md#required-acceptance-evidence-before-cryptex-enables-writes). Include a normal refresh with an edit pending, followed by reopening the vault. The previous edit must either be safely reconciled with its verified base or retained for explicit review. Check that the adjacent user note and the newly published note keep their expected contents and that no canonical event appears without daemon acceptance. These are proposed acceptance cases. No native trial, plugin, mount or managed write was performed in this review.
